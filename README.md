## ✨ Что это такое

**ЭЛОУ-АВТ Smart Tutor** — это fullstack-приложение, которое симулирует работу реальной промышленной установки первичной переработки нефти. Оператор управляет клапанами и нагревом через SCADA-интерфейс в реальном времени, а встроенный ИИ-модуль:

- 🔮 **Предсказывает** риски аварии на 15 секунд вперёд (LSTM-нейросеть, ONNX Runtime)
- 🧠 **Анализирует ошибки** оператора через алгоритм выравнивания последовательностей LCS (Longest Common Subsequence)
- 🔒 **Защищает** результаты обучения от фальсификации (JWT + SHA-256 + соль)
- 🌐 **Изолирует сессии** (Multi-Session Simulation Architecture)

> 💡 **Границы MVP-версии:** Прототип воспроизводит сквозной учебный маршрут **ЭЛОУ → АТ → ВТ**. Наиболее детально реализована динамическая модель **атмосферного блока (печь П-1 — колонна К-1)**: температура, давление, уровень куба, клапаны, блокировки. Блоки **ЭЛОУ** (солесодержание, обводнённость) и **ВТ** (остаточное давление К-2, температура куба) представлены агрегированными моделями с причинно-следственными связями с атмосферным блоком; их детализация — приоритет следующей итерации.
>
> ⚠️ Тренажёр предназначен для обучения и предварительной оценки учебных действий. Он **не является средством управления технологическим процессом** и не служит единственным основанием допуска персонала к работе на реальной установке.

## 🚀 Быстрый старт

### Вариант 0: Через Makefile (самый короткий путь)

В корне проекта лежит `Makefile` с четырьмя командами на весь цикл работы (`make` без аргументов покажет этот список):
```bash
make init    # создать .env из шаблона и установить зависимости (Python + npm)
make start   # собрать и поднять весь стек в Docker, дождаться готовности
make stop    # остановить стек (база в томе сохраняется)
make lint    # проверить код: oxlint во фронтенде + синтаксис Python
```

Настройки вынесены в отдельный файл **`config.mk`** — там задаются используемые инструменты (`docker compose`, `python3`, `npm`), пути к исходникам и порты по умолчанию. Значения можно переопределить и на лету, не редактируя файлы:
```bash
make start COMPOSE="podman compose"
```

> ⚠️ **Версия Node.** Фронтенду нужен Node `^20.19` или `>=22.12` (требование oxlint, Vite 7 и React 19). На более старом Node установка молча пропускает бинарные пакеты линтера, поэтому `make init` и `make lint` заранее проверяют версию и подсказывают, что делать. Переключиться можно через `nvm use 22`, после чего переустановить зависимости: `make init`.

Ниже — те же операции подробно и без Make, если он недоступен.

### Вариант 1: Единый запуск (фронтенд + бэкенд одновременно)
Самый простой способ запустить всё одной командой из корня проекта:

API бэкенда будет работать на: http://127.0.0.1:8000/

### Вариант 2: Раздельный локальный запуск

Все команды выполняются из корня проекта:

#### 1. Запуск только бэкенда (API и Симулятор)

*(Или напрямую: `python -m uvicorn elou_tutor.api.main:app --host 127.0.0.1 --port 8000`)*

#### 2. Запуск только фронтенда (Интерфейс)
```bash
npm run frontend
```
*(Или напрямую: `cd frontend && npm run dev`)*

### Вариант 3: Запуск через Docker Compose (всё в одном)

Полный стек в двух контейнерах: **бэкенд** (FastAPI + симулятор + ИИ-ядро) и **фронтенд** (собранный React под nginx, который проксирует `/api` и `/ws` на бэкенд). Ставить Python и Node.js локально не нужно — достаточно Docker.

#### 1. Создайте файл `backend/.env` с секретами

Бэкенду обязательно нужны переменные `INTEGRITY_SALT` (соль для хэша целостности сессий) и `SECRET_KEY` (подпись JWT) — без них контейнер не стартует. Готовый шаблон с dev-значениями лежит в репозитории:
```bash
cp backend/.env.example backend/.env
```
Сам `backend/.env` в `.gitignore` и в репозиторий не попадает. Для продакшена замените значения на случайные, например `openssl rand -hex 32`.

#### 2. Соберите и запустите стек
```bash
docker compose up --build
```
Первая сборка занимает несколько минут (npm-сборка фронтенда и установка Python-зависимостей), последующие запуски — секунды.

| Сервис | Адрес | Примечание |
|---|---|---|
| **Интерфейс тренажёра** | http://localhost:8080/ | порт задан в `docker-compose.yml` |
| **API бэкенда** | http://localhost:8000/ | порт задан в `docker-compose.yml` |
| **Проверка живости** | http://localhost:8000/api/health | отвечает `{"status":"ok"}` |

> 💡 **Про порты.** Фронтенд поднимается на `8080`, а не на стандартном `80`: последний часто занят (Docker Desktop, OrbStack, локальный nginx). Нужен другой порт — правьте `ports` в `docker-compose.yml`.

Войдите под демо-учётной записью — оператор `operator_1` или инструктор `instructor_1`, пароль `Ktk_2026!` (полный список выше). Роль в форме входа должна совпадать с ролью учётной записи, иначе сервер откажет в доступе.

#### 3. Полезные команды
```bash
docker compose up -d --build     # запустить в фоне
docker compose logs -f backend   # смотреть логи бэкенда
docker compose ps                # статус контейнеров и healthcheck
docker compose down              # остановить стек (данные сохранятся)
docker compose down -v           # остановить и стереть БД тренажёра
```

#### Как всё устроено

* **Хранение данных.** База `tutor.db` лежит в именованном томе `tutor_data`, поэтому сессии обучения и журнал аудита переживают перезапуск и пересборку контейнеров. Полностью сбросить базу можно только через `docker compose down -v`.
* **Порядок запуска.** У бэкенда настроен healthcheck по `/api/health`; nginx стартует только после того, как API готов принимать запросы, — на первых секундах не будет ошибок `502`.
* **Живая разработка.** Исходники пакета (`backend/src`) смонтированы в контейнер, uvicorn запущен с `--reload`, а `PYTHONPATH` указывает на смонтированный каталог — иначе Python брал бы копию из образа и перезагрузка была бы холостой. Правки Python-кода применяются без пересборки. Изменения во фронтенде требуют `docker compose up --build frontend`.
* **Отдельный образ для облака.** Корневой `Dockerfile` — это другая, одноконтейнерная сборка для деплоя на Render и Hugging Face Spaces (FastAPI отдаёт и API, и собранную статику на порту `$PORT`). Для локальной работы он не нужен.

Проверка целостности из тест-кейса 5 в Docker выполняется внутри контейнера — путь к базе там другой:
```bash
docker compose exec backend python -c "import sqlite3; conn = sqlite3.connect('/app/data/tutor.db'); conn.execute('UPDATE training_sessions SET score = 100 WHERE id = (SELECT max(id) FROM training_sessions)'); conn.commit(); conn.close(); print('Успешно скомпрометировано!')"
```

## 🎮 Что тестировать и как (Функционал КТК)

Компьютерный тренажерный комплекс содержит два независимых веб-интерфейса (К1: Разделение экранов) с передачей телеметрии и команд по WebSockets в реальном времени.

### 1. Панель Оператора (http://localhost:5173/)
* **Мнемосхема SCADA:** Отображает динамические датчики: Температура печи П-1 (T-1), Давление в колонне К-1 (P-1), Уровень куба К-1 (L-1).
* **Органы управления:**
  - Переключение клапанов: Вход сырья V-1, Аварийный сброс V-2, Дренаж куба V-3.
  - Управление нагревом: Ползунок уставки температуры печи П-1.
  - Кнопка аварийного останова (ESD) для глушения установки.
* **ИИ-Мониторинг:**
  - Живой график предиктивного тренда параметров на 15 секунд вперед.
  - Индикатор риска аварии (Risk Level, %) на основе LSTM-модели.
  - Персональные всплывающие предупреждения ИИ по регламенту.

### 2. Панель Инструктора (http://localhost:5173/ с переключением роли)
* **Управление сценарием:** Выбор пуска/останова и сброс сессии.
* **Инъекция неисправностей (Слайд 11 КТК):**
  - **Отказ сырьевого насоса Н-1** (прекращает подачу сырья, угроза сухого хода П-1).
  - **Прогар змеевика П-1** (критический перегрев змеевиков, риск пожара).
  - **Зависание клапана V-2** (блокировка сброса давления в факел, угроза взрыва).
* **Аудит обучения и ИБ:**
  - База данных сессий с проверкой контрольной суммы результатов по ГОСТ (хэширование SHA-256 с солью для исключения фальсификации).
  - **Интерактивный разбор:** Кликните по любой строке в таблице сессий — откроется центрированное модальное окно с детальным ScoreCard (оценка, точечные нарушения регламента и рекомендации ИИ) и полным посекундным логом действий оператора за эту попытку.

## 🧪 Сценарии для тестирования

### Тест-кейс 1. Управление параметрами и балансом колонны (Тест-кейс 2.1 и 2.2)
1. Войдите как `Тест_Оператор` (сырьевой V-1 и дренаж V-3 по умолчанию открыты, V-2 закрыт).
2. Измените уставку температуры печи П-1 на `340°C`. Наблюдайте плавный рост температуры и давления в колонне К-1 (датчик Р-1).
3. При росте давления выше `0.4 МПа` **откройте клапан сброса V-2** (он станет зеленым). Давление в колонне начнет снижаться и стабилизируется в районе `0.31 МПа`.
4. Верните уставку температуры П-1 на номинальные `280°C`, после чего закройте клапан сброса **V-2** (он станет красным).
5. Переведите клапан дренажа **V-3 в положение ЗАКРЫТ** (кнопка станет красной). Уровень куба колонны К-1 начнет расти.
6. Снова **откройте V-3** (зеленый), чтобы стабилизировать уровень на исходном значении (около 50%).
7. Нажмите кнопку «Завершить» для сохранения результатов сессии.

### Тест-кейс 2. Парирование отказа сырьевого насоса (Тест-кейс 7.1)
1. Инструктор включает дефект **«Отказ сырьевого насоса»**.
2. У оператора прекращается подача сырья (расход падает), фактическая температура печи П-1 начинает ползти вверх. Уровень в кубе начинает падать на -0.6% в секунду.
3. Operator обязан немедленно **снизить уставку температуры печи П-1 (SP_DOWN) до минимума**, предотвратив сухой перегрев змеевиков.
4. При своевременном снижении температуры ИИ-ассистент зафиксирует успешную локализацию нештатной ситуации. Если оператор бездействует — через ~70 секунд сработает блокировка по падению уровня ниже 5% (авария).

### Тест-кейс 3. Авария при заклинившем клапане сброса V-2 (Тест-кейс 8.1)
1. Инструктор включает дефект **«Заедание клапана сброса V-2»**.
2. Оператор поднимает уставку температуры печи П-1 до `340°C`, провоцируя рост давления.
3. При давлении выше `0.4 МПа` оператор пытается открыть клапан сброса **V-2** (зеленый), но давление продолжает расти, так как клапан механически заклинило.
4. Для предотвращения взрыва колонны оператор обязан вручную **запустить аварийный останов (кнопка ESD)**.
5. Если оператор бездействует — при давлении `0.48 МПа` произойдет автоматическая блокировка ПАЗ с фиксацией аварии (взрыв К-1).

### Тест-кейс 4. Переполнение колонны К-1 по высокому уровню (Тест-кейс 9.1)
1. Operator **закрывает дренаж V-3** (клапан станет красным), оставив вход сырья V-1 открытым.
2. Наблюдайте рост уровня куба К-1. При превышении `85%` появится предупреждение.
3. При достижении уровня `98%` симуляция прерывается автоматической блокировкой ПАЗ (авария по переполнению куба, риск уноса жидкости в шлемовую линию).

### Тест-кейс 5. Контроль целостности ИБ (Тест-кейс 6.1)
1. В таблице сессий панели инструктора все записи отображаются со статусом целостности `OK` (хэш валиден).
2. Чтобы сымитировать несанкционированное изменение данных в БД злоумышленником (без установки стороннего ПО для SQLite), выполните в консоли Python-однострочник из корня проекта:
   ```bash
   python -c "import sqlite3; conn = sqlite3.connect('backend/tutor.db'); conn.execute('UPDATE training_sessions SET score = 100 WHERE id = (SELECT max(id) FROM training_sessions)'); conn.commit(); conn.close(); print('Успешно скомпрометировано!')"
   ```
3. Обновите страницу панели инструктора. Система пересчитает хэш SHA-256 с секретной солью, мгновенно обнаружит подмену оценки и выведет красное предупреждение **«Нарушена!»** вместо зеленого `OK`.

## 🏗 Архитектура репозитория (Monorepo)

*   📂 **`backend/`** — вся серверная часть:

Подробная карта репозитория, правило зависимостей между слоями и «куда смотреть для типичной задачи» — в [docs/architecture.md](docs/architecture.md).

## ⚙️ Под капотом (Архитектура и логика работы)

Проект построен по модульному принципу (Monorepo) с четким разделением ответственности компонентов. Ниже описано, как устроена работа комплекса на низком уровне.

### 1. Архитектура взаимодействия (Data Flow)
```
+------------------+                   +--------------------+
|  React Фронтенд  | <--(WebSockets)-->|  FastAPI Бэкенд    |
|  (мнемосхема)    |                   |  (sim.step / tick) |
+------------------+                   +----------+---------+
                                                  |
                                                  v
                                       +----------+---------+
                                       |  predictive_engine |
                                       |  (LSTM / polyfit)  |
                                       +----------+---------+
                                                  |
                                                  v
                                       +----------+---------+
                                       |   error_analyzer   |
                                       |   (LCS / Rules)    |
                                       +--------------------+
```
* **WebSocket-канал:** Каждую секунду бэкенд рассылает текущее состояние симулятора (`sensors`, `valves`, `setpoints`, `logs`, `riskLevel`, `predictions`) всем подключенным клиентам (операторам и инструкторам).
* **События управления:** При кликах по клапанам или ползунку температуры фронтенд мгновенно отправляет экшен-пакет (JSON), который бэкенд применяет к математической модели.

### 2. Математическая модель (`backend/src/elou_tutor/simulation/model.py`)
* Реализована динамика тепломассообмена физических процессов ЭЛОУ-АВТ:
  - **Температура печи П-1:** Рассчитывается динамически с учетом подачи холодного сырья (функция охлаждения сырьем с компенсацией feedforward) и уставки горелок.
  - **Давление колонны К-1:** Зависит от температуры паров из печи и уровня заполнения куба. Снижается при открытии клапана сброса `V-2` в факел.
  - **Уровень куба К-1:** Зависит от объема входящего сырья `V-1` и расхода дренажа `V-3`.
* Встроена логика блокировок ПАЗ (противоаварийная защита) по критическим уставкам: давление $>0.48$ МПа (взрыв колонны) или перегрев $>380$ °C (пожар змеевиков).

### 3. Нейросетевой ИИ-предиктор (`backend/src/elou_tutor/ml/predictor.py`)
* **Стек:** ONNX Runtime в рантайме; PyTorch — только в офлайн-обучении (`backend/training/`), в прод-образ не входит.
* **Принцип:** 
  - Накапливает в памяти 30-секундное скользящее окно из 7 параметров (состояния всех клапанов, уставка и фактические показатели датчиков).
  - Входное окно нормируется в диапазон `[0, 1]`.
  - Модель **LSTM** (2 слоя, 64 скрытых нейрона) прогнозирует значения датчиков на 15 секунд вперед.
  - **Отказоустойчивость:** Если ONNX Runtime недоступен или модель не загрузилась, автоматически подключается математический экстраполятор тренда (полиномиальная регрессия `numpy.polyfit` по последним 10 точкам).
  - На основе прогнозов вычисляется интегральный риск аварии (%) в зависимости от скорости приближения параметров к аварийным границам.

### 4. LCS и семантический разбор ошибок (`backend/src/elou_tutor/tutor/analyzer.py`)
* **LCS (Longest Common Subsequence):** Вычисляет наибольшую общую подпоследовательность между массивом кликов оператора и «золотой последовательностью» регламента. Позволяет оценить очередность действий независимо от пауз и темпа работы оператора.
* **Логический анализатор (Rules Tree):** На бэкенде анализируется семантика действий:
  - *Сухой ход печи:* Попытка повысить нагрев печи (`SP_UP`) до открытия подачи сырья (`V1_OPEN`).
  - *Горячий останов:* Перекрытие подачи сырья (`V1_CLOSE`) при работающем нагреве.
  - *Блокировка дренажа:* Закрытие `V-3` при активном входе `V-1`, ведущее к переполнению.
  - *Форсированный разогрев:* Быстрая серия кликов повышения температуры без выдержки времени на стабилизацию.
* По итогам выдается текстовая подсказка со ссылкой на пункты технологического регламента и автоматически назначается подходящая адаптивная траектория повторного обучения.

### 5. Безопасность и контроль целостности (ИБ)
* Результаты обучения оператора защищены от подделки: при записи сессии рассчитывается хэш SHA-256 по формуле:
  `Hash = SHA256(SessionData + SECRET_SALT)`

* База данных сессий при запросе пересчитывает хэш для каждой строки. Если кто-то вручную изменил лог или оценку в SQLite, система обнаружит нарушение целостности и выдаст предупреждение `Нарушена!`.
