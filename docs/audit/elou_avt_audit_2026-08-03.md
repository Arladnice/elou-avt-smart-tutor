## 1. Краткий вердикт

1. **Статус: готов как MVP, условно готов к защите.** Есть работоспособный веб-тренажёр с backend, React-интерфейсом, WebSocket, ролями, сессиями, оценкой и ONNX-инференсом; однако промышленная готовность и заявленные эксплуатационные свойства не доказаны.
2. **Текущая оценка: 3.2 / 5.** Это сильный технический прототип атмосферного блока П‑1/К‑1, а не цифровой двойник полного комплекса ЭЛОУ‑АВТ.
3. **Реалистичный потолок к 14.08 после P0/P1: 4.0 / 5.** Достижим только при честном сужении позиционирования, чистом Docker-demо и приложении результатов performance/restore-проверок.
4. **Сильная сторона №1:** связанная вертикаль «UI → JWT/WebSocket → симулятор → ML/risk → журнал/score», а не набор скриншотов: `frontend/src/app/providers/SimulatorProvider.tsx`, `backend/src/elou_tutor/api/routes/ws.py`, `simulation/model.py`, `ml/predictor.py`.
5. **Сильная сторона №2:** воспроизводимо прошли 156 pytest-проверок, ruff, import-linter, TypeScript/Vite build, frontend lint и FSD-check.
6. **Сильная сторона №3:** ML честнее большинства MVP: датасет помечен синтетическим, разделение по `session_id` есть, в отчёте признаны Precision ≈2.7% и непригодность для реальной установки.
7. **Опасный риск №1:** в UI есть явный offline/demo fallback без токена (`LoginPage.tsx:44–49`, `SimulatorProvider.tsx:79`), что на защите может создать впечатление авторизации/RBAC там, где backend фактически обходится.
8. **Опасный риск №2:** документация смешивает MVP с целевой enterprise-архитектурой (Kubernetes/HA/TLS/backup/50+ сессий), без соответствующей реализации или результатов испытаний.

## 3. Существенные несоответствия «документация ↔ код»

1. **«ЭЛОУ‑АВТ» против реализованной модели атмосферного блока.** В ТЗ (`docs/requirements.md:58`) заявлены материальные и тепловые балансы установки; в сводной записке есть корректная оговорка MVP (`…:9`). Код `backend/src/elou_tutor/simulation/model.py` моделирует только T/P/L, setpoint и V1–V3 для П‑1/К‑1, без потоков сырья/фракций, теплообменников, ЭЛОУ, вакуумной секции, ректификационных контуров и валидированной физики. **High.** Допустимо: «интерактивная упрощённая динамическая модель атмосферного участка П‑1/К‑1 для учебных сценариев».
2. **Промышленная инфраструктура описана как целевой контур, но не реализована.** `docs/infrastructure.md`, `solution_architecture.md` и `security_threat_model.md` описывают HA, Kubernetes, TLS 1.3/WSS, backup и мониторинг; в репозитории отсутствуют Helm/K8s manifests, Prometheus/Grafana, backup/restore automation, reverse proxy with TLS и результаты нагрузочного теста. **High.** Допустимо: «целевой контур спроектирован; MVP запускается в Docker и не имеет подтверждённого SLA».
3. **>50 одновременных сессий и 99.9% uptime.** Заявлено в `docs/Сводная_пояснительная_записка.md:76`; найден health/metrics, но отсутствуют k6/Locust/JMeter сценарий, отчёт и HA. **High.** Допустимо: «нагрузочная цель пилота, не измеренный показатель MVP».
4. **«HMAC» в traceability.** `docs/traceability_matrix.md:10` ссылается на несуществующие `test_integrity.py`, `test_audit.py`; актуальная проверка находится в `tests/test_integrity_and_rbac.py` и `tests/test_tutor.py`. HMAC реализован, но трассируемость устарела. **Medium.** Исправить ссылки до защиты.
5. **«Транспорт защищён TLS 1.3/WSS».** `docs/security_threat_model.md:55` — это требование/целевой дизайн. В checked-in Compose/Docker нет TLS termination/certificate configuration. **High.** Допустимо: «TLS должен обеспечиваться внешним reverse proxy в пилоте; в локальном MVP не доказан».
6. **«Данные журнала юридически значимы / основание допуска».** `security_threat_model.md:16`; фактически SQLite, HMAC integrity, но нет неизменяемого внешнего журнала, управления ключами, регламента, квалифицированной подписи или сертификации. **High.** Допустимо: «учебный audit trail с контролем целостности; не юридически значимая аттестация».
7. **ML «предотвращает аварии».** В `…Сводная…:995` формулировка слишком сильная. `training/data_generator.py:15–20` генерирует synthetic data из того же симулятора, а отчёт имеет только 2 positive cases из 10,330 и Precision 0.03. **Critical.** Допустимо: «на синтетическом holdout модель выдаёт 15-секундный прогноз T/P/L и учебный risk signal; не валидирована для реальной установки».
8. **RBAC в demo mode.** Документация представляет RBAC как системную меру, но `frontend/src/pages/login/ui/LoginPage.tsx:44–49` при ошибке backend логинит как `operator`, а `SimulatorProvider.tsx:79, 341–366` разрешает offline состояние без JWT/WS. **High.** Допустимо: «RBAC действует только в online server mode; offline demo mode не является защищённым режимом».

## 4. Технический аудит

### Архитектура и развёртывание

**Реализовано.** Backend/FastAPI и frontend/Vite разделены; контейнерные файлы, `.env.example`, Makefile и GitHub Actions присутствуют. Backend dependency graph прошёл `lint-imports`: 6 контрактов, 0 нарушений. Frontend production build успешен.

**Проблемы.**
- Docker Compose не был запущен, потому что в среде нет Docker daemon. Следовательно, утверждение README о запуске «с нуля» пока непроверенное именно в контейнерном виде.
- Целевая HA/backup/monitoring архитектура документальна. В кодовой базе нет развёртываемого механизма её исполнения.
- В frontend build есть основной chunk 704.58 kB minified (232.67 kB gzip): предупреждение Vite, не blocker, но P2 для слабых корпоративных сетей.

### Backend/API

**Реализовано.** API и WS защищают роли токеном; тесты покрывают forged JWT, scope/RBAC и WS взаимодействие (`tests/test_security_hardening.py`, `test_tutor.py:559+`). Сессионные логи и integrity hash проверяются. ONNX runtime изолирован от PyTorch runtime.

**Проблемы.**
- Смысл параметров `role`/`username` в URL WebSocket не должен считаться источником прав: их необходимо визуально и тестом сопоставлять с claims токена. Существующие тесты хороши, но на демо следует показать именно rejected mismatch.
- Не найдено доказательство production-grade распределённого rate limiting: in-memory ограничения не выдерживают multi-replica. Для MVP это допустимо, для заявленного HA — нет.
- SQLite подходит демонстрации, но не конкурентному многопользовательскому production-контру без стратегии WAL/backup/migration/locking.

### Frontend/UX

**Реализовано.** `npm ci`; `npm run build`, `lint`, `check:fsd` завершились успешно. UI реально строит WS URL c token (`SimulatorProvider.tsx:361–366`), отображает роли и тренды.

**Критичный продуктовый дефект.** Login fallback (`LoginPage.tsx:44–49`) silently запускает локального оператора, если API недоступен. Это опасно: экран может выглядеть как защищённый продукт, хотя данные, RBAC, audit и backend-валидация не участвуют. 

**Минимальное исправление:** убрать fallback из production build либо показывать большую неснимаемую плашку «ЛОКАЛЬНЫЙ СИМУЛЯТОР — БЕЗ АВТОРИЗАЦИИ, ДАННЫЕ НЕ СОХРАНЯЮТСЯ», отдельный route/feature flag `VITE_DEMO_MODE=false` по умолчанию.

### Безопасность

**Подтверждено:** JWT, bcrypt/passlib, RBAC, HMAC-SHA256, серверная проверка целостности, ограничения payload/WS и SSRF validation имеют код и тесты. Это сильнее, чем просто модель угроз.

**Не подтверждено/не реализовано как production control:** TLS/WSS, внешнее управление secrets, persistent/distributed rate limiting, SIEM, backup/restore, независимый pentest, SAST/dependency scan в CI. `npm ci` обнаружил одну high-severity dependency vulnerability: нельзя игнорировать перед демонстрацией — нужна команда `npm audit --omit=dev`/проверка, уязвимый пакет и применимость должны быть зафиксированы.

Нельзя говорить о фактическом соответствии ФЗ‑152, ФЗ‑187, УЗ‑3, ГОСТ Р 57580 или КИИ: проект содержит дизайн и частичные controls, не юридическое/сертифицированное соответствие.

### ML и данные

**Факты.** Есть `backend/src/elou_tutor/ml/artifacts/model.onnx` (212,530 bytes), checkpoint, CSV ≈6.2 MB, scripts `data_generator.py`, `train.py`, `export_onnx.py`, `evaluate.py`. Генератор прямо создаёт **синтетическую** телеметрию из `ELOUAVTSimulator` (`data_generator.py:15–22`). LSTM получает 30x7, прогнозирует T/P/L на t+15 (`train.py:34–63`). Разделение по session id уменьшает оконную утечку (`train.py:126–143`, `evaluate.py:38–89`).

**Ограничения, которые нельзя замазывать.**
- Датасет не из реальной ЭЛОУ‑АВТ, не показаны источники, паспорт, экспертная валидация коэффициентов, дрейф, noise/датчики или out-of-distribution тест.
- Метрики аварийной классификации строятся поверх всего двух положительных окон: Recall=1.00 означает «обнаружены 2 из 2», а не статистически устойчивую 100% полноту. Precision≈0.03 означает примерно 73 ложные тревоги на 2 true positive; F1≈0.05. Это не допустимый production alarm predictor.
- Модель обучается regression MSE T/P/L, а аварийная классификация выводится через rule/threshold risk. Поэтому утверждать «LSTM классифицирует аварии» некорректно; корректнее «LSTM прогнозирует параметры, из прогноза вычисляется учебный риск».
- Lead time 15 sec задан горизонтом target (`FORECAST_HORIZON`), но нет анализа фактического time-to-event/стабильности предупреждения и сравнения нескольких горизонтов.

### Производительность и эксплуатация

Latency measurement и health/metrics — полезные заготовки. Но результатов p50/p95/p99, RPS, памяти/CPU, 50 WS sessions, behaviour after reconnect, backup restore и disaster recovery не найдено. Поэтому все SLA/throughput цифры — цели, не факты.

### Документация и воспроизводимость

Документация очень объёмна, но чрезмерно смешивает «реализовано», «целевое состояние» и «предположение». Плюс есть локальные `file:///e:/Git-Projects/...` ссылки (`docs/Сводная_пояснительная_записка.md:621` и др.), которые на чужом компьютере не открываются. Исправить на относительные markdown links. `team_tasks.md` сам показывает незакрытые задачи по Docker/SSRF/модели угроз — это полезная честность, но не материал для жюри в текущем виде.

### 15 неприятных вопросов и честные ответы

1. **Это полный ЭЛОУ‑АВТ?** — Нет, MVP атмосферного блока П‑1/К‑1; граница специально зафиксирована.
2. **Откуда данные?** — Synthetic telemetry, generated from our simulator; реальных данных нет.
3. **Почему Recall 100%?** — Это 2/2 positive windows, не доказательство промышленной надёжности.
4. **Почему Precision 2.7%?** — Слишком много false positives; для учебного exploration допустимо, для production alarm — нет.
5. **Модель классифицирует аварию?** — Она прогнозирует T/P/L; risk label получается пороговым правилом поверх прогноза.
6. **Где физическая валидация?** — Её нет; требуется технологическая экспертиза и калибровка на архиве.
7. **Почему называть это двойником?** — В узком учебном смысле: модель состояния и реакции ограниченного процесса; не industrial-grade twin.
8. **Кто имеет права?** — В online-mode backend JWT/RBAC; offline demo mode не является безопасным и маркируется/отключается.
9. **Можно подделать оценку?** — Сервер проверяет HMAC целостности записи; это не заменяет юридически значимый неизменяемый журнал.
10. **Есть TLS?** — В MVP локально не доказан; для пилота TLS должен завершаться в reverse proxy.
11. **Выдержит 50 сессий?** — Это целевой KPI, пока не подтверждён нагрузочным отчётом.
12. **Как восстанавливаете БД?** — Для MVP SQLite; formalised backup/restore — ближайший P1, не заявляем RTO/RPO до drill.
13. **Почему SQLite?** — Быстро и прозрачно для demo/MVP; production pilot потребует managed PostgreSQL/backup policy.
14. **Как защищаете реальные OT-системы?** — MVP не подключается к DCS/АСУ ТП; любая интеграция требует отдельного OT security design.
15. **Какой следующий gate?** — Экспертная валидация модели П‑1/К‑1 и data-sharing пилот: реальные исторические данные, calibration, shadow testing.
