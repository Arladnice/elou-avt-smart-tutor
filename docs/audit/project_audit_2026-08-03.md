# Аудит готовности ELOU-AVT Smart Tutor к защите

**Дата проверки:** 03.08.2026  
**Основание:** кейс, критерии оценивания, папка `docs/` и фактический код репозитория.

## Короткий вывод

Проект — **работоспособный и убедительный MVP для защиты**, но его нельзя честно называть промышленно готовым цифровым двойником всей ЭЛОУ‑АВТ. Реализация сильнее, чем часть документации: 03.08 успешно прошли **156 backend-тестов**; фронтенд собирается production-сборкой. Главная опасность — не падение приложения, а завышенные заявления в документации/презентации без доказательств: промышленная инфраструктура, полный охват установки, качество ИИ и измеренная производительность.

Моя оценка на текущем состоянии: **3,6–3,9 / 5** (ориентировочно 72–78%). С хорошей демонстрацией и устранением P0/P1-замечаний реальна зона **4 / 5**.

## Критические проблемы

### P0 — исправить или честно ограничить до защиты

1. **Не смешивать MVP и промышленное решение.**  
   `docs/solution_architecture.md`, `docs/infrastructure.md` и сводная записка описывают Kubernetes, мониторинг, резервирование и контейнер на сессию, однако фактически запуск подтверждён Docker Compose. На каждом слайде и в ответах разделять: **«реализовано сейчас»** и **«целевая архитектура следующего этапа»**.

2. **Не заявлять полный цифровой двойник ЭЛОУ‑АВТ.**  
   Корректная формула для защиты: *«интерактивный учебный MVP атмосферного блока с архитектурой расширения на АТ/ВТ»*. Иначе эксперт попросит показать не реализованные технологические маршруты.

3. **Закрыть секреты для production.**  
   В `backend/src/elou_tutor/api/security.py` и `backend/src/elou_tutor/domain/integrity.py` есть значения по умолчанию. Для production контейнер должен отказываться стартовать без сильных `SECRET_KEY` и `INTEGRITY_SALT`; dev-значения допустимы только в тестах/локальном профиле. Также заменить ключи короче 32 байт: тестовый прогон уже показывает предупреждения PyJWT.

4. **Не продавать модель как предиктор аварий реальной установки.**  
   Это синтетическая учебная модель. В защите назвать её *модулем раннего предупреждения учебного симулятора*, показать полный recall и lead time, а Precision 2,7% объяснить как цену консервативного порога — с планом калибровки на архивной телеметрии.

### P1 — сильнее всего поднимет оценку

5. **Производительность и эксплуатация.** Добавить один воспроизводимый отчёт: конфигурация, 5–10 одновременных сессий, p95 REST/WebSocket latency, CPU/RAM, результат и ограничения. Без него К7 останется документальным.

6. **Трассируемость.** Создать таблицу по ключевым требованиям: ID требования, экран/API, автотест/ручной тест, доказательство в демо, статус. Это одновременно усиливает К1, К2 и К6.

7. **Согласовать документы.** `main_strategic_plan.md` содержит спорные/устаревшие самооценки; заменить локальные `file:///e:/...` на относительные ссылки. Исправить ссылку из `docs/team_tasks.md` на `docs/security_threat_model.md`.

## Что показать комиссии за 7–10 минут

1. Вход оператором и инструктором; запрет операции при другой роли.
2. Запуск аварийного сценария, действия обучаемого, ESD и скоринг.
3. Экран инструктора: сессии, таймлайн и аудит.
4. Раннее предупреждение ИИ с честным пояснением ограничений модели.
5. Один слайд: «MVP сегодня / промышленный контур после пилота».
6. Финальный слайд с 156 passed, production build, измерениями нагрузки (после их проведения) и ссылкой на матрицу трассируемости.

## Проверено фактически

- Backend: `pytest -q` — **156 passed**, 42 предупреждения, 54 subtests; время 8,46 с.
- Frontend: `npm ci && npm run build` — успешно. Есть предупреждение: основной bundle ~705 kB minified; для MVP не блокер, но стоит обозначить code splitting как технический долг.
- В WebSocket реализованы проверка JWT/роли и получение имени из токена; прежнее замечание о свободной подмене роли по query-параметру в актуальном коде уже не подтверждается.
