# Производительность WebSocket

**Дата измерения:** 4 августа 2026 года  
**Метрика:** прикладной RTT сообщения `ping` → `pong` по тому же WebSocket-протоколу, который использует frontend  
**Объём:** 100 последовательных запросов, пауза 50 мс между запросами

## Результаты

| Контур | Min | Среднее | Медиана | P95 | P99 | Max |
|---|---:|---:|---:|---:|---:|---:|
| Локальный backend, `ws://127.0.0.1:8765` | 0,76 мс | 1,74 мс | 1,37 мс | 2,74 мс | 10,02 мс | 15,49 мс |
| Публичный стенд, `wss://tutor.kluknulo.ru` | 4,77 мс | 9,55 мс | 5,93 мс | 11,84 мс | 49,06 мс | 252,98 мс |

## Вывод

На публичном стенде типичная задержка составляет **5,93 мс**, а 95% измерений укладываются в **11,84 мс**. Требование `< 100 мс` выполняется для 99% выборки. Зафиксирован единичный выброс 252,98 мс, поэтому на защите корректно заявлять медиану и P95, а не гарантированный максимум.

## Методика

1. Выполнен вход штатной учётной записью оператора через `POST /api/auth/login`.
2. Открыто авторизованное соединение `/ws` с ролью `operator`.
3. Для каждого замера клиент сохранял монотонное локальное время, отправлял JSON `{"type":"ping","timestamp":N}` и ожидал соответствующий `{"type":"pong","timestamp":N}`.
4. RTT рассчитывался по `time.perf_counter_ns()`, поэтому изменение системных часов не влияет на результат.
5. Служебные кадры телеметрии, приходящие между `ping` и `pong`, пропускались.

Это end-to-end замер приложения, включающий WebSocket, TLS и reverse proxy публичного стенда. Он не является нагрузочным тестом и не подтверждает целевое число параллельных сессий.
