## 1. Контекст и назначение системы

КТК ЭЛОУ-АВТ Smart Tutor — компьютерный тренажёрный комплекс (КТК) установки первичной переработки нефти. Система не подключена к действующей АСУ ТП и не управляет реальным оборудованием. Её назначение — обучение операторов управлению виртуальной установкой в режиме безопасной симуляции.

### Пользователи и их роли

| Роль | Количество одновременных пользователей | Критичность простоя |
|---|---|---|
| Оператор | ≤ 10 (MVP) | Высокая: прерывание учебного сеанса |
| Инструктор | ≤ 3 (MVP) | Высокая: потеря управления сценарием |
| Администратор | 1 | Средняя: управленческие функции |

### Текущий технологический стек (MVP)

```
Caddy (HTTPS) → Nginx (frontend, :80) → FastAPI (backend, :8765)
                                        ├── SimulationSession (in-memory)
                                        ├── ONNX Runtime (CPU)
                                        ├── TF-IDF RAG (in-memory)
                                        └── SQLite (WAL, файл на диске)
```

**Ключевые ограничения архитектуры MVP:**
- Состояние активной симуляции хранится только в памяти процесса FastAPI
- SQLite-файл находится на том же хосте, что и backend
- Нет автоматического резервного копирования и restore-теста
- Нет централизованного мониторинга и алертинга
- Единственный хост без резервирования

## 2. Компоненты системы и классы критичности

Классификация основана на трёх факторах:
- **Операционный ущерб** — насколько потеря компонента нарушает основную функцию (обучение операторов)
- **Восстановимость данных** — возможность восстановления без резервных копий
- **Уникальность данных** — данные создаются пользователями и не могут быть воспроизведены автоматически

### Класс A — Критичный (максимальная важность)

Потеря компонента немедленно прекращает обучение и/или приводит к безвозвратной потере уникальных данных.

| Компонент | Данные | Причина критичности |
|---|---|---|
| **SQLite (база данных)** | Учётные записи, результаты сессий, журнал аудита | Уникальные данные операторов; восстановление без резервной копии невозможно |
| **FastAPI backend** | Точка входа для всех клиентов | Полная недоступность системы при отказе |
| **Состояние симуляции (in-memory)** | Текущий учебный сеанс | Потеря прогресса текущего упражнения; не персистируется |

### Класс B — Важный (существенная важность)

Потеря компонента деградирует функциональность, но система остаётся частично доступной.

| Компонент | Данные | Причина важности |
|---|---|---|
| **ONNX ML-модель (risk predictor)** | Веса модели (`model.onnx`) | При отказе система переключается на численный baseline; обучение продолжается |
| **RAG / база знаний** | Документы техрегламента | ИИ-чат деградирует, основной сценарий работает |
| **Caddy (TLS-прокси)** | TLS-сертификаты Let's Encrypt | Недоступность HTTPS блокирует внешних пользователей |

### Класс C — Вспомогательный (низкий приоритет)

Потеря компонента не прерывает текущую работу пользователей.

| Компонент | Данные | Причина низкого приоритета |
|---|---|---|
| **Frontend (Nginx + SPA)** | Статические файлы | Пересборка из репозитория занимает минуты; данные пользователей не теряются |
| **ML-обучение (`ml_training/`)** | Офлайн-артефакты | Не входит в прод-образ; влияет только на будущие версии модели |
| **Nginx reverse-proxy** | Конфигурация | Восстанавливается из конфига за секунды |

## 3. Расчёт RPO по компонентам

**RPO (Recovery Point Objective)** — допустимый объём потери данных, выраженный во времени: сколько последних данных может быть утрачено без критического ущерба для работы системы.

### Факторы расчёта RPO

#### 3.1 Масштаб операционных и финансовых потерь при аварии

КТК — тренажёрная система без прямой связи с производством. Операционные потери выражаются в:
- **Потере результатов учебной сессии:** одна сессия = 30–120 минут работы оператора; стоимость повторного прохождения оценивается в 1–2 чел.-часа тренинга
- **Потере журнала аудита:** нарушение требований 149-ФЗ и регламентов ИБ в части неотказуемости; потенциальные претензии при инциденте
- **Потере учётных записей:** критично, восстановление требует администраторского вмешательства; риск НСД при некорректном восстановлении

#### 3.2 Вероятность аварии

| Угроза | Вероятность (MVP, единственный хост) | Обоснование |
|---|---|---|
| Сбой диска / хоста | Средняя | VPS без RAID, типичный MTBF диска ~3–5 лет |
| Некорректный деплой (CI/CD) | Низкая–средняя | GitHub Actions → deploy.yml выполняет `docker compose up --build`; нет staging |
| Атака (ransomware, удаление данных) | Низкая (MVP — не критическая инфраструктура) | Анализ векторов атак задокументирован в `attack_vectors_templates.md` |
| Программная ошибка / corruption SQLite | Низкая | WAL-режим снижает риск; при аварийном завершении процесса возможна потеря последних транзакций |

#### 3.3 Количество приложений, использующих набор данных

- SQLite используется **только одним процессом** (FastAPI backend); параллельная запись исключена
- Нет репликации и нет внешних потребителей БД
- Отсутствие внешних зависимостей снижает риск расхождения состояний, но увеличивает уязвимость к единой точке отказа

#### 3.4 Стоимость стратегии резервного копирования

| Стратегия | Стоимость (инфраструктура) | Накладные расходы (разработка) |
|---|---|---|
| SQLite `.backup()` каждый час (cron) | ~0 (на том же хосте, локальный диск) | 1–2 часа: cron-скрипт + alert |
| SQLite backup на внешнее S3-хранилище (ежечасно) | ~$1–5/мес (S3 хранение) | 4–6 часов: скрипт + IAM + тест restore |
| PostgreSQL WAL-репликация (пилот) | Доп. VPS ~$10–20/мес | Значительный рефакторинг (несколько дней) |

#### 3.5 Существующие правила хранения данных

- **Журнал аудита** (`audit.py`) — цепочка блоков с HMAC-SHA256; требует неизменности (ГОСТ Р 56939, 149-ФЗ). RPO = 0 нежелателен только технически, фактически цель — не допустить потери событий аудита
- **Сессии обучения** — без явных нормативных требований к хранению, но корпоративная практика нефтяной отрасли предполагает хранение результатов обучения не менее 3–5 лет
- **Пользовательские данные (ПДн)** — согласно 152-ФЗ, оператор обязан обеспечить целостность данных; потеря требует уведомления субъектов

### RPO по компонентам

| Компонент | Целевой RPO | Обоснование |
|---|---|---|
| **SQLite: журнал аудита** | **0** (нулевой) | Требование неотказуемости; потеря событий аудита нарушает целостность цепочки |
| **SQLite: результаты сессий** | **1 час** | Потеря одной сессии — до 1 ч. работы оператора; ежечасной резервной копии достаточно |
| **SQLite: учётные записи** | **24 часа** | Обновляются редко; суточная резервная копия покрывает типичный производственный режим |
| **Состояние симуляции (in-memory)** | **0** (по дизайну) | Не персистируется: потеря при рестарте — нормальное поведение MVP; сессия начинается заново |
| **ML-модель (model.onnx)** | **Нет потери** | Файл хранится в репозитории (Git) и пакете; восстанавливается из образа |
| **База знаний RAG** | **Нет потери** | Статические документы в репозитории; восстанавливаются из образа |
| **Frontend (статика)** | **Нет потери** | Артефакт сборки; восстанавливается из репозитория |

## 4. Расчёт RTO по компонентам

**RTO (Recovery Time Objective)** — максимально допустимое время восстановления работоспособности системы после аварии.

### Факторы расчёта RTO

#### 4.1 Ущерб организации при разрушении системы

| Сценарий отказа | Прямой ущерб | Косвенный ущерб |
|---|---|---|
| Полный отказ backend | Прерывание всех активных учебных сессий | Невозможность проведения запланированных тренингов; простой инструкторов и операторов |
| Потеря данных БД | Потеря результатов аттестации | Юридическая ответственность (152-ФЗ); повторное прохождение операторами упражнений |
| Недоступность ≥ 4 часов | Срыв учебного плана смены | Операционные издержки нефтехимического предприятия: недообученный персонал = повышенный риск аварии |

#### 4.2 Критичность и стоимость простоя

Для учебной системы нефтехимического предприятия:
- **Оценка стоимости простоя:** 1 час простоя = ~2–5 чел.-часов специалистов (оператор + инструктор + администратор) + организационные потери
- **Критичность:** высокая при проведении плановых тренингов; низкая в нерабочее время
- **Окно обслуживания:** нерабочие часы (ночью, выходные) — допустимое время для плановых работ

#### 4.3 Предполагаемая продолжительность простоя

| Тип отказа | Ожидаемое время без автоматизации | С автоматизацией (цель пилота) |
|---|---|---|
| Падение контейнера (crash) | 1–5 мин (ручной рестарт) | < 1 мин (restart: unless-stopped) |
| Некорректный деплой | 15–30 мин (откат вручную) | 5–10 мин (CI rollback job) |
| Отказ хоста / VPS | 30–120 мин (провизионинг нового) | 15–30 мин (snapshot restore) |
| Повреждение БД | 1–4 часа (ручное восстановление из архива) | 15–30 мин (автоматизированный restore) |

#### 4.4 Текущие уязвимости системы

1. **Единственная точка отказа:** один VPS без резервирования хоста
2. **In-memory состояние симуляции:** потеря при любом рестарте процесса (нет персистентности)
3. **SQLite без внешнего backup:** потеря хоста = потеря всех данных
4. **Отсутствие healthcheck-алертинга:** обнаружение отказа только при обращении пользователя
5. **WebSocket stale-timeout не верифицирован:** зависшее соединение не освобождает сессию автоматически

#### 4.5 Реализованные меры защиты активов

| Мера | Реализовано | Файл |

#### 4.6 Потенциальные угрозы, релевантные для системы

| Угроза | Вероятность | Влияние на RTO |
|---|---|---|
| Ошибка деплоя (сломанный образ) | Средняя | +15–30 мин (ручной откат) |
| Исчерпание дискового пространства | Средняя (рост аудита) | Полный отказ backend; +30–60 мин |
| Отказ Let's Encrypt (истечение сертификата) | Низкая (авто-продление) | HTTPS недоступен; +5–15 мин |
| DDoS / исчерпание сокетов | Низкая | Деградация; +15–60 мин |
| Ransomware / удаление данных | Очень низкая | Полное восстановление из резервной копии; +60–240 мин |

### RTO по компонентам

| Компонент | Тип отказа | Целевой RTO |
|---|---|---|
| **FastAPI backend (контейнер)** | Краш контейнера | **< 1 мин** (Docker restart policy) |
| **FastAPI backend (некорректный деплой)** | Сломанный образ | **< 15 мин** (откат к предыдущему образу) |
| **Состояние симуляции** | Краш backend | **< 2 мин** (новая сессия; данные текущей теряются по дизайну) |
| **SQLite** | Повреждение файла | **< 30 мин** (восстановление из резервной копии) |
| **Caddy / TLS** | Ошибка конфигурации | **< 10 мин** (рестарт + проверка сертификата) |
| **Frontend** | Ошибка сборки | **< 20 мин** (пересборка из репозитория) |
| **Хост / VPS** | Полный отказ хоста | **< 60 мин** (восстановление из snapshot + docker compose up) |
| **ML-модель (ONNX)** | Повреждение файла | **< 5 мин** (восстановление из Docker-образа или репозитория) |

## 6. Техническое решение по обеспечению RTO и RPO

### 6.1 MVP (текущее состояние) — что уже реализовано

**1. Docker restart policy (`unless-stopped`)**
- Файл: `docker-compose.yml` → `services.backend.restart: unless-stopped`
- Результат: RTO при краше контейнера < 1 мин

**2. SQLite WAL-режим**
- Файл: `elou_tutor/db/database.py` → `PRAGMA journal_mode=WAL`
- Результат: снижение риска corruption при аварийном завершении

**3. Аудит с HMAC-цепочкой**
- Файл: `elou_tutor/db/audit.py`
- Результат: RPO аудита — целостность на уровне транзакций

**4. ONNX fallback (numerical baseline)**
- Файл: `elou_tutor/ml/predictor.py`
- Результат: деградированная работа системы при отказе ML-модели; RTO = 0

**5. Caddy auto-TLS (Let's Encrypt)**
- Файл: `docker-compose.prod.yml` → `caddy_data` volume
- Результат: сертификат переживает пересоздание контейнера; авто-продление

### 6.2 Приоритетные меры для закрытия разрывов (до пилота)

#### Шаг 1 — Автоматический backup SQLite (~4–6 ч. разработки)

```bash
#!/bin/bash
# /opt/elou-backup/backup.sh — запускается cron каждый час
BACKUP_DIR=/opt/elou-backup/snapshots
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
DB_PATH=/var/lib/elou/elou_tutor.db

# Используем SQLite Online Backup API (безопасно при работающем процессе)
sqlite3 "$DB_PATH" ".backup '$BACKUP_DIR/elou_tutor_$TIMESTAMP.db'"

# Хранить последние 48 копий (48 часов)
find "$BACKUP_DIR" -name "*.db" -mtime +2 -delete

# Копировать на внешнее S3
aws s3 cp "$BACKUP_DIR/elou_tutor_$TIMESTAMP.db" \
  s3://elou-backups/db/ --storage-class STANDARD_IA
```

Достигаемые показатели: RPO результатов сессий = 1 час ✅; RPO учётных записей = 24 часа ✅

#### Шаг 2 — Restore-тест (обязательно до пилота)

```bash
# Еженедельный тест восстановления:
# 1. Остановить backend → восстановить из последней резервной копии
# 2. Запустить backend → проверить количество пользователей
# 3. Проверить целостность цепочки аудита
python -m pytest backend/tests/test_restore_integrity.py -v
```

#### Шаг 3 — Healthcheck в docker-compose (~2–4 ч.)

```yaml
services:
  backend:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8765/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
```

#### Шаг 4 — VPS snapshot (~30 мин. настройки)

Ежедневный автоматический snapshot хоста через API облачного провайдера.
- Стоимость: ~$1–3/мес.
- Даёт RTO при полном отказе хоста < 60 мин без резервного хоста

### 6.3 Целевой пилот

| Мера | Компонент | Достигаемый эффект |
|---|---|---|
| PostgreSQL + Point-in-Time Recovery | БД | RPO → минуты; замена SQLite |
| Redis session store | Симуляция | Состояние переживает рестарт backend |
| Kubernetes (liveness/readiness probe) | Backend | RTO краша < 30 сек; rolling update без простоя |
| Staging-среда в CI/CD | Весь стек | Исключение сломанных деплоев в prod |
| Prometheus + Grafana + алертинг | Мониторинг | Обнаружение отказа за секунды |
| Мультизонный деплой (2 VPS) | Хост | RTO при отказе хоста < 5 мин |
| Корпоративный IAM (LDAP/AD) | Auth | Независимость от локальной БД пользователей |

## 7. Потенциальные угрозы и уязвимости

Детальный анализ векторов атак задокументирован в
[`attack_vectors_templates.md`](./attack_vectors_templates.md) и
[`security_threat_model.md`](./security_threat_model.md).

### 7.1 Угрозы, влияющие на RTO и RPO

| Угроза | Вектор | Влияние на RTO/RPO | Мера противодействия |
|---|---|---|---|
| Ошибочный деплой | CI/CD без staging | RTO +15–30 мин | Staging + ручное подтверждение prod deploy |
| Переполнение диска (рост аудита) | Неограниченный рост `elou_tutor.db` | RTO +30–60 мин | Ротация аудита; disk space alert |
| Corruption SQLite при OOM-kill | Ядро убивает процесс при нехватке памяти | RPO = с последней WAL-checkpoint | WAL + ежечасный backup |
| DDoS / исчерпание WebSocket | Массовые соединения | RTO +15–60 мин | Rate limiting на Caddy |
| Истечение TLS-сертификата | Ошибка авто-продления (занят порт 80) | RTO +5–15 мин | Мониторинг даты истечения; alert за 30 дней |
| Ransomware | НСД + шифрование диска | RPO = последний offsite backup | Offsite backup на S3 |

### 7.2 Риск единственной точки отказа (SPOF)

```
Единственный VPS
├── Caddy (SPOF для HTTPS)
├── Nginx (SPOF для frontend)
├── FastAPI (SPOF для backend)
└── SQLite файл (SPOF для данных)
```

Все компоненты работают на одном хосте. Отказ хоста = полная недоступность системы.
**Цель пилота:** разнести БД и backend на разные хосты; добавить второй backend для failover.

## 8. Ограничения MVP и план развития

> [!WARNING]
> Следующие показатели являются **целями**, а не измеренными характеристиками MVP:
> - SLA 99,9% (достижимо только при мультизонном деплое)
> - 50 параллельных активных сессий (нагрузочный тест не проводился)
> - Автоматический backup и restore-тест (не реализованы)
> - RTO < 60 мин при отказе хоста (зависит от скорости snapshot-restore у провайдера)

### Roadmap от MVP к пилоту

```
MVP (текущий)                       Пилот (целевой)
──────────────────────────────────  ──────────────────────────────────────
SQLite (локальный файл)          →  PostgreSQL (отдельный хост + PiTR)
Нет backup                       →  Hourly backup → S3; restore-тест еженедельно
In-memory симуляция              →  Redis session store
Один VPS                         →  2 зоны (primary + standby)
Нет мониторинга                  →  Prometheus + Grafana + алертинг
CI/CD напрямую в prod            →  Staging → smoke test → prod (rollback)
```

### Соответствие нормативным требованиям

| Требование | Источник | Текущий статус | Целевой статус |
|---|---|---|---|
| Целостность данных оператора | 149-ФЗ ст. 16 | HMAC-аудит ✅ | + внешний backup ✅ |
| Защита ПДн (восстановление) | 152-ФЗ + ФСТЭК №21 ЗИС.3 | Частично (WAL) | PostgreSQL PiTR ✅ |
| Неотказуемость журнала аудита | ГОСТ Р 56939; 149-ФЗ | HMAC-цепочка ✅ | + append-only log ✅ |
| Уведомление об инцидентах | 152-ФЗ ст. 21.1 | Не автоматизировано | Alerting → оператор ✅ |
