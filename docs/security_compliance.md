## 1. Уровень защищённости ПДн (ПП РФ № 1119)

**Источник:** Постановление Правительства РФ от 01.11.2012 № 1119 «Об утверждении требований к защите персональных данных при их обработке в информационных системах персональных данных».

### 1.1. Исходные параметры системы

| Параметр | Значение |
|---|---|
| Тип обрабатываемых ПДн | **Иные** (фамилия, имя, должность, результаты обучения) |
| Категория субъектов | **Сотрудники** оператора |
| Количество субъектов | **Менее 100 000** |
| Тип актуальных угроз | **Угрозы 3-го типа** (только уязвимости прикладного ПО; угрозы, связанные с НДВ в системном ПО и аппаратуре, не актуальны для MVP) |

### 1.2. Определение уровня защищённости

Согласно **п. 11** ПП РФ № 1119, при сочетании:
- иных ПДн,
- субъектов — сотрудников,
- угроз 3-го типа,

устанавливается **УЗ 4 (четвёртый уровень защищённости)**.

> **п. 11** ПП РФ № 1119: «Для обеспечения 4-го уровня защищённости персональных данных при их обработке в информационных системах необходимо выполнение следующих требований: а) организация режима обеспечения безопасности помещений; б) обеспечение сохранности носителей персональных данных; в) утверждение руководителем оператора документа, определяющего перечень лиц, доступ которых необходим; г) использование СЗИ, прошедших процедуру оценки соответствия».

### 1.3. Обязательные требования для УЗ 4

Согласно **п. 11** ПП РФ № 1119:

| № | Требование | Статус в MVP |
|---|---|---|
| а | Организация режима обеспечения безопасности помещений с техническими средствами | Применимо при развёртывании у заказчика |
| б | Обеспечение сохранности носителей ПДн | SQLite-файл защищён правами файловой системы |
| в | Перечень лиц с доступом к ПДн, утверждённый руководителем | Требует оформления до пилота |
| г | Применение СЗИ, прошедших процедуру оценки соответствия | Требует оценки при переходе к пилоту |

> **Примечание:** Согласно п. 5 ПП РФ № 1119, уровень защищённости определяется оператором самостоятельно с учётом актуальных угроз. Перечень актуальных угроз 3-го типа фиксируется в модели угроз и нарушителя, которая разрабатывается до начала обработки ПДн.

## 2. Меры защиты ПДн (Приказ ФСТЭК № 21)

**Источник:** Приказ ФСТЭК России от 18.02.2013 № 21 «Об утверждении состава и содержания организационных и технических мер по обеспечению безопасности персональных данных при их обработке в ИСПДн».

### 2.1. Базовый набор мер для УЗ 4

Согласно **п. 2** и **Приложению** к Приказу № 21, для **УЗ 4** применяется базовый набор мер:

| Код меры | Наименование | Реализовано в КТК |
|---|---|---|
| **ИАФ.1** | Идентификация и аутентификация пользователей | JWT-токены, bcrypt паролей |
| **ИАФ.5** | Защита обратной связи при вводе аутентификационной информации | Пароль скрыт при вводе |
| **УПД.1** | Управление учётными записями пользователей | RBAC: роли operator / instructor / admin |
| **УПД.2** | Реализация необходимых методов (дискреционный) управления доступом | Проверки прав на каждом эндпоинте |
| **УПД.5** | Назначение минимально необходимых прав и привилегий | Оператор не имеет доступа к сессиям других |
| **РСБ.1** | Определение событий безопасности, подлежащих регистрации | Логируются входы, команды, результаты |
| **РСБ.2** | Определение состава и содержания информации о событиях | user_id, timestamp, IP, action |
| **РСБ.5** | Мониторинг (просмотр, анализ) результатов регистрации | Ручной просмотр; автоматизация — до пилота |
| **ЗНИ.1** | Учёт машинных носителей информации | Применимо при развёртывании у заказчика |
| **ОЦЛ.1** | Контроль целостности программного обеспечения | HMAC-SHA256 записей аудита |
| **ОДТ.2** | Резервное копирование информации | SQLite WAL включён; backup-процесс не подтверждён |
| **ЗИС.1** | Разделение в системе функций по управлению и по эксплуатации | Разделение admin/instructor/operator |

### 2.2. Адаптация и дополнение базового набора (п. 4 Приказа № 21)

Оператор вправе исключить неприменимые меры и добавить компенсирующие.
Для MVP исключены меры, относящиеся к многоуровневым сетевым сегментам и физическим носителям, как неприменимые к учебному стенду.

## 3. Требования по защите АСУ ТП (Приказ ФСТЭК № 31)

**Источник:** Приказ ФСТЭК России от 14.03.2014 № 31 «Об утверждении требований к обеспечению защиты информации в АСУ ТП на критически важных объектах».

### 3.1. Применимость к КТК

> **Важная оговорка:** Приказ № 31 регулирует **реальные АСУ ТП** на критически важных и потенциально опасных объектах. КТК ЭЛОУ-АВТ Smart Tutor является **учебным симулятором**, физически не подключённым к SCADA/DCS реального производства. Формальная обязанность по выполнению Приказа № 31 возникает только если тренажёр будет интегрирован в контур реальной АСУ ТП или признан значимым объектом КИИ.

### 3.2. Применимые принципы из Приказа № 31

Несмотря на необязательность, ниже приведены требования, которые применяются как ориентиры проектирования:

| Пункт Приказа № 31 | Требование | Статус в КТК |
|---|---|---|
| **п. 6** | Защита от НСД к информации, обрабатываемой в АСУ ТП | JWT + RBAC |
| **п. 6** | Обеспечение целостности конфигурации и данных | HMAC-SHA256 аудит-лога |
| **п. 6** | Регистрация событий безопасности | Audit log в SQLite |
| **п. 7** | Классы защищённости систем (3А, 2Б и т.д.) | Классификация проводится при реальном внедрении |
| **п. 14** | Применение СЗИ, прошедших оценку соответствия | Требует сертификации при переходе к пилоту |
| **п. 21** | Управление доступом (разграничение прав) | Роли operator / instructor / admin |
| **п. 26** | Регистрация событий (аудит) | Все команды оператора логируются с timestamp и session_id |
| **п. 33** | Защита от внешних воздействий и атак | Rate-limit WebSocket, anti-SSRF, нормализация путей |

## 4. Требования 149-ФЗ «Об информации»

**Источник:** Федеральный закон от 27.07.2006 № 149-ФЗ «Об информации, информационных технологиях и о защите информации».

### 4.1. Ключевые статьи, применимые к КТК

| Статья | Содержание | Реализация в КТК |
|---|---|---|
| **Ст. 16, ч. 1** | Защита информации — принятие правовых, организационных и технических мер, обеспечивающих: конфиденциальность, целостность, доступность | JWT, RBAC, HMAC, WAL, HTTPS |
| **Ст. 16, ч. 2** | Оператор обязан обеспечить защиту от НСД, от случайного доступа, от уничтожения, изменения, блокирования, копирования, предоставления, распространения | RBAC, bcrypt, HMAC audit; шифрование БД — до пилота |
| **Ст. 16, ч. 4** | Требования к защите государственных информационных систем устанавливаются федеральными органами | N/A: КТК не является ГИС |

## 5. Требования 152-ФЗ «О персональных данных»

**Источник:** Федеральный закон от 27.07.2006 № 152-ФЗ «О персональных данных».

### 5.1. ПДн в КТК

В тренажёре обрабатываются следующие ПДн сотрудников (операторов и инструкторов):

- Имя, фамилия (для идентификации в системе)
- Результаты учебных сессий (оценки, таймлайн действий)
- Данные о роли и должности

### 5.2. Применимые статьи

| Статья | Требование | Реализация |
|---|---|---|
| **Ст. 18.1** | Оператор обязан принимать меры для выполнения обязанностей, предусмотренных законом: назначить ответственного, издать документы, ознакомить сотрудников | Требует оформления до пилота |
| **Ст. 19, ч. 1** | Оператор обязан принимать технические и организационные меры защиты ПДн от НСД, уничтожения, изменения, блокирования, копирования | JWT, bcrypt, RBAC, HMAC |
| **Ст. 19, ч. 2** | Правительство РФ устанавливает уровни защищённости ПДн (→ ПП РФ № 1119) | см. Раздел 1 |
| **Ст. 19, ч. 3** | Контроль мер защиты осуществляет ФСТЭК России (технические) и ФСБ России (криптография) | Проверка при пилоте |
| **Ст. 22** | Оператор обязан уведомить Роскомнадзор об обработке ПДн | До начала реальной обработки ПДн |
| **Ст. 5** | Принципы обработки ПДн: законность, ограничение целей, минимизация объёма, точность, хранение не дольше необходимого | MVP хранит только данные сессий; срок хранения не определён |
| **Ст. 9** | Согласие субъектов ПДн на обработку | Форма согласия требуется при пилоте |

### 5.3. Что реализовано в коде

- `bcrypt` хэширование паролей (`domain/credentials.py`)
- HMAC-SHA256 целостности записей аудита (`domain/integrity.py`)
- JWT-аутентификация с ролями (`api/security.py`)
- Audit log с фиксацией всех действий (`db/audit.py`)

## 6. Требования 187-ФЗ «О безопасности КИИ»

**Источник:** Федеральный закон от 26.07.2017 № 187-ФЗ «О безопасности критической информационной инфраструктуры Российской Федерации».

### 6.1. Применимость к КТК

> **Ключевая оговорка (из лекции экспертов ГПН):** Искусственное завышение уровня критичности системы является типичной ошибкой участников. Классификация учебного тренажёра как объекта КИИ без должного обоснования — не плюс, а минус.

КТК ЭЛОУ-АВТ Smart Tutor:
- **Не подключён** к реальным промышленным системам управления
- **Не является** частью технологического процесса НПЗ
- **Не влияет** на физическую безопасность установки ЭЛОУ-АВТ

**Вывод:** Формальные требования 187-ФЗ **не применяются** к MVP. Применение возможно только если оператор (Газпром нефть) признает тренажёрный комплекс объектом КИИ в ходе категорирования по **ст. 7** 187-ФЗ.

### 6.2. Что изменится при признании объектом КИИ

| Статья 187-ФЗ | Требование |
|---|---|
| **Ст. 7** | Проведение категорирования объектов КИИ (I, II или III категория) |
| **Ст. 8** | Создание и ведение реестра объектов КИИ (ГосСОПКА) |
| **Ст. 9** | Обеспечение безопасности объекта КИИ, реагирование на инциденты |
| **Ст. 10** | Организация мониторинга и взаимодействия с ГосСОПКА (НКЦКИ) |
| **Ст. 12** | Реализация планов по обеспечению устойчивого функционирования |

## 9. Требования Приказа ФСТЭК № 17 / ГОСТ Р 56939

**Источники:**
- Приказ ФСТЭК России от 11.02.2013 № 17 «Об утверждении требований о защите информации, не составляющей государственную тайну, содержащейся в государственных информационных системах».

## 11. Векторы НСД и меры противодействия

### 11.1. Получение несанкционированного доступа к серверу КТК

| Вектор атаки | Описание | Меры противодействия | Реализовано |
|---|---|---|---|
| **Брутфорс пароля** | Перебор паролей к /api/auth/login | Rate-limit (max 5 попыток / 15 мин), временная блокировка IP, bcrypt (cost=12) | Реализовано |
| **Утечка JWT-токена** | Перехват токена из заголовков или логов | TLS, запрет логирования токенов, короткий TTL токена (1ч), httpOnly cookies | Частично |
| **SQL-инъекция** | Манипуляция запросами к SQLite | Параметризованные запросы (SQLAlchemy ORM), запрет прямой конкатенации в SQL | Реализовано |
| **Path Traversal** | Обращение к ../../etc/passwd через API | Нормализация путей os.path.normpath, whitelist допустимых директорий | Реализовано |
| **SSRF** | Принудительный запрос от сервера к внутренней сети | Валидация схемы, DNS-resolv, блокировка private/link-local адресов | Реализовано |
| **Компрометация SSH** | Доступ к серверу через SSH с украденными credentials | Запрет парольного SSH, только ключи; fail2ban; запрет root-login | До пилота |
| **Supply Chain атака** | Вредоносный пакет в зависимостях | pip-audit, npm audit, фиксация версий в requirements.txt / package-lock.json | До пилота |
| **Эксплуатация CVE в компонентах** | Уязвимости в FastAPI, Uvicorn, React | Регулярное обновление; Dependabot в CI | До пилота |

### 11.2. Подмена логов и результатов обучения

| Вектор атаки | Описание | Меры противодействия | Реализовано |
|---|---|---|---|
| **Прямая запись в БД** | Правка SQLite напрямую с доступом к серверу | HMAC-SHA256 каждой записи аудита (domain/integrity.py); несовпадение хэша — запись помечается как скомпрометированная | Реализовано |
| **Подмена через API** | Отправка поддельных команд от имени оператора | JWT-проверка: каждое действие подписано токеном пользователя; session_id привязан к пользователю | Реализовано |
| **Replay-атака** | Повтор записанных WebSocket-команд | Проверка временной метки команды (допустимое окно ±30 с); уникальный session_id | Частично |
| **Фальсификация ScoreCard** | Изменение итоговой оценки после завершения сессии | Оценка пересчитывается из неизменяемого audit-лога; ScoreCard не хранится как отдельное редактируемое поле | Реализовано |
| **Удаление логов** | rm -rf /var/log или DELETE FROM audit_log | Ротация логов с append-only режимом; WAL SQLite; HMAC делает бессмысленным избирательное удаление | Частично |
| **Инъекция в лог** | Вставка поддельных записей | HMAC привязан к user_id + timestamp + action; поддельная запись без правильного ключа будет обнаружена | Реализовано |

### 11.3. Защита от инсайдерской угрозы (Privileged User Abuse)

- Действия admin-роли логируются так же, как и operator/instructor
- Изменение прав пользователя логируется в audit_log с указанием инициатора
- Запрет самоназначения прав: API проверяет, что пользователь не повышает собственную роль

## 12. Безопасность ИИ-алгоритмов, мониторинг и аудит

### 12.1. Защита ИИ-моделей от компрометации

**Источники:**
- OWASP Machine Learning Security Top 10 (ML01–ML10) — https://owasp.org/www-project-machine-learning-security-top-10/
- Лекция ГПН: «Атаки на ИИ-модели и загрязнение данных (Data Poisoning)»
- ГОСТ Р 56939-2016, п. 5.1–5.6

| Угроза (OWASP ML) | Описание | Реализованная мера |
|---|---|---|
| **ML01** Data Poisoning | Загрязнение обучающих данных | Синтетические данные генерируются детерминированным алгоритмом с фиксированным seed; датасет хэшируется |
| **ML02** Model Inversion | Извлечение обучающих данных через API инференса | API возвращает только скалярное значение риска (0–100), не веса модели |
| **ML03** Model Stealing | Кража модели через массовый инференс | API недоступен публично; ONNX-файл не экспонируется клиенту |
| **ML05** Model Repudiation | Подмена модели в production | ONNX-файл верифицируется SHA-256 хэшем при каждом старте сервера |
| **ML06** AI Supply Chain | Уязвимые версии torch/onnxruntime | torch присутствует только в backend/training/ (вне prod-образа); рантайм использует onnxruntime |
| **ML09** Output Integrity | Манипуляция выходными данными | Значение риска передаётся по WSS; клиент не может подменить его на сервере |

### 12.2. Мониторинг и аудит действий пользователей

Реализовано согласно **Приказу ФСТЭК № 21, РСБ.1–РСБ.5** и **Приказу ФСТЭК № 239, РСБ**:

#### Что логируется (audit_log):

| Событие | Поля | Хранение |
|---|---|---|
| Успешный вход | user_id, IP, timestamp UTC, user_agent | SQLite audit_log |
| Неудачная попытка входа | IP, timestamp, username (если передан) | SQLite audit_log |
| Команда оператора | user_id, session_id, action_type, payload_hash, timestamp | SQLite audit_log |
| Результат сессии (ScoreCard) | user_id, session_id, score, timestamp | SQLite + HMAC |
| Изменение прав пользователя | admin_user_id, target_user_id, old_role, new_role, timestamp | SQLite audit_log |
| Старт/останов сценария | user_id, scenario_id, timestamp | SQLite audit_log |

#### Чего не логируется:
- Пароли и токены в plain-text (152-ФЗ ст. 19; лекция ГПН)
- Содержимое ПДн в логах (152-ФЗ ст. 19)
- Избыточные технические события — каждый WebSocket heartbeat (лекция ГПН)

#### Защита лога:
- HMAC-SHA256 каждой записи (`domain/integrity.py`)
- При старте сервера — проверка целостности последних N записей
- Ротация логов: `logs/audit_{date}.log` (планируется)

### 12.3. Схемы реагирования на инциденты, связанные с ИИ

| Инцидент | Признак обнаружения | Действие |
|---|---|---|
| Аномальные выходные значения риска | Риск стабильно 0 или 100 при нормальной телеметрии | Автоматический алерт; fallback на rule-based оценку |
| Нарушение целостности ONNX-модели | SHA-256 не совпадает | Отказ запуска сервера; уведомление администратора |
| Data Poisoning (при переобучении) | Резкое изменение метрик val_loss при одинаковых данных | Откат к предыдущей версии модели (версионирование артефактов) |
| Prompt Injection (RAG/LLM-чат) | Нетипичные запросы к чат-API | Санитизация входа; ограничение контекста; логирование запроса |

## 13. План реагирования на инциденты ИБ

**Основание:** Приказ ФСТЭК № 21, меры ИНЦ.1–ИНЦ.4; Приказ ФСТЭК № 239, ИНЦ; лекция ГПН (SOC и DFIR).

### 13.1. Классификация инцидентов

| Приоритет | Критерий | Примеры |
|---|---|---|
| **P1 — Критический** | Компрометация данных или системы, недоступность сервиса | Утечка ПДн, взлом учётной записи admin, подмена audit-лога |
| **P2 — Высокий** | Попытка атаки с частичным успехом, нарушение целостности | Множественные неудачные входы, несовпадение HMAC |
| **P3 — Средний** | Подозрительная активность без явного ущерба | Нетипичные запросы к API, ошибки авторизации |
| **P4 — Низкий** | Единичные аномалии, предупреждения | Ротация логов не выполнена, TTL токена истёк |

### 13.2. Пошаговый план реагирования (7 фаз)

**Цикл:** ОБНАРУЖЕНИЕ → ОЦЕНКА → СДЕРЖИВАНИЕ → РАССЛЕДОВАНИЕ → УСТРАНЕНИЕ → ВОССТАНОВЛЕНИЕ → АНАЛИЗ

#### Фаза 1: Обнаружение (Detection)
- Автоматические алерты (audit_log: аномальные HMAC, множественные failed logins)
- Ручной мониторинг логов инструктором/администратором
- Сообщение пользователя о подозрительном поведении

**Инструменты:** `GET /api/admin/audit-log` (admin-эндпоинт), grep по `auth_failed` в логах.

#### Фаза 2: Оценка (Assessment) — не более 15 минут для P1
1. Определить приоритет (P1–P4) по таблице 13.1
2. Установить предварительный масштаб: какие данные/компоненты затронуты
3. Зафиксировать время обнаружения, IP-адрес, user_id

#### Фаза 3: Сдерживание (Containment)

| Инцидент | Немедленное действие |
|---|---|
| Компрометация УЗ пользователя | PATCH /api/admin/users/{id} — деактивация УЗ; инвалидация JWT (blacklist) |
| DDoS / флуд WebSocket | Блокировка IP на уровне nginx/firewall; усиление rate-limit |
| Подмена данных | Перевод системы в read-only режим; изоляция скомпрометированного тома |
| Утечка секретов | Ротация JWT_SECRET, HMAC_KEY в .env; перезапуск backend |

#### Фаза 4: Расследование (Investigation — DFIR)

1. Экспорт audit_log с проверкой HMAC каждой записи
2. Построение таймлайна событий (поля timestamp UTC, session_id, user_id, IP)
3. Корреляция событий: логины → команды → изменения данных
4. Сохранение снапшота SQLite-файла как доказательства

> **Важно (лекция ГПН):** Единый NTP-сервер критичен — без синхронизации времени построение таймлайна расследования невозможно.

#### Фаза 5: Устранение (Eradication)

- Изменение скомпрометированных credentials
- Применение патча или конфигурационного исправления
- Удаление вредоносных артефактов (если обнаружены)
- Пересборка Docker-образа из чистого репозитория при подозрении на компрометацию ПО

#### Фаза 6: Восстановление (Recovery)

- Восстановление из резервной копии SQLite (последний чистый WAL-snapshot)
- Проверка целостности ONNX-модели (SHA-256)
- Поэтапный ввод системы в работу под усиленным мониторингом
- Уведомление пользователей (при необходимости — в соответствии со ст. 21 152-ФЗ)

#### Фаза 7: Анализ после инцидента (Post-Incident Review)

| Артефакт | Срок |
|---|---|
| Отчёт об инциденте (что, когда, кто, последствия) | не позднее 72 часов |
| Root Cause Analysis | не позднее 7 дней |
| Обновление модели угроз | не позднее 30 дней |
| Изменение кода/конфигурации (если требуется) | не позднее 30 дней |

## 14. Изолированная среда и быстрый сброс до чистой копии

**Основание:** Приказ ФСТЭК № 21, ОДТ.2 (резервное копирование); Приказ ФСТЭК № 239, ЗИС.1 (управление доступом к ресурсам); принцип Defence in Depth (лекция ГПН).

### 14.1. Архитектура изоляции

Каждая учебная симуляция в КТК ЭЛОУ-АВТ Smart Tutor выполняется **внутри Docker-контейнера**, изолированного от хостовой операционной системы и от остальных компонентов стека:

```
┌─────────────────────────── Хостовая ОС ────────────────────────────┐
│                                                                     │
│  ┌──────────────────┐   Docker-сеть   ┌────────────────────────┐   │
│  │  tutor-frontend  │ ←────────────── │    tutor-backend       │   │
│  │  (nginx, React)  │   только внутри │  FastAPI + Simulator   │   │
│  └────────┬─────────┘   контейнерной  │  + ONNX risk model     │   │
│           │              сети Docker  └──────────┬─────────────┘   │
│           │                                      │                 │
│   127.0.0.1:8080                         том tutor_data           │
│   (loopback only)                        (SQLite БД)              │
│           ↑                                                         │
│      Caddy / TLS                                                    │
│   (только prod)                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 14.2. Реализованные меры изоляции

| Механизм | Описание | Подтверждение |
|---|---|---|
| **Контейнеризация** | Симулятор и API работают в отдельном Docker-контейнере `tutor-backend` | `docker-compose.yml`, строка 7 |
| **Сетевая изоляция** | Порты API (`8000`) и frontend (`8080`) привязаны к `127.0.0.1` — не доступны напрямую из интернета | `docker-compose.yml`, строки 14–15, 49–50 |
| **Разделение фронта и бэкенда** | Два отдельных контейнера; frontend стартует только после прохождения healthcheck бэкенда | `docker-compose.yml`, строки 51–53 |
| **Изоляция данных** | Единственное пересечение с хостом — именованный том `tutor_data`; исходный код монтируется read-only в dev-режиме | `docker-compose.yml`, строки 16–19 |
| **TLS-терминация** | В prod весь внешний трафик идёт через Caddy с автосертификатом Let's Encrypt | `docker-compose.prod.yml` |
| **Healthcheck** | Backend не считается готовым до успешного HTTP-ответа на `/api/health` | `docker-compose.yml`, строки 33–38 |

### 14.3. Быстрый сброс до чистой копии

Три команды в [Makefile](../Makefile), реализованные специально для сценария «сброс среды»:

| Команда | Действие | Когда использовать |
|---|---|---|
| `make reset` | Остановить стек → удалить том `tutor_data` (БД) → поднять чистый стек | После учебной сессии, перед новой демонстрацией |
| `make reset-hard` | Остановить → удалить том + локальные образы → пересобрать с `--no-cache` → поднять | При подозрении на компрометацию образа или после обновления зависимостей |
| `make snapshot` | Сохранить резервную копию БД в `./backups/tutor_<timestamp>.db` | Перед `reset`, если сессию нужно сохранить |

**Рабочий процесс безопасной демонстрации:**

```bash
# 1. Сохранить текущее состояние (если нужно)
make snapshot

# 2. Сбросить до чистой копии
make reset

# 3. Стенд готов — открыть http://localhost:8080
```

**Жёсткий сброс (после обновления кода или при подозрении на компрометацию):**

```bash
make reset-hard
```

### 14.4. Нормативное обоснование изолированной среды

| Требование | НПА | Реализация |
|---|---|---|
| Разграничение доступа к компонентам системы | Приказ ФСТЭК № 21, УПД.2; Приказ ФСТЭК № 239, ЗИС.1 | Docker-сети изолируют frontend/backend; API не доступен напрямую |
| Резервное копирование перед изменениями | Приказ ФСТЭК № 21, ОДТ.2 | `make snapshot` сохраняет БД с временной меткой |
| Возможность восстановления до известного состояния | Приказ ФСТЭК № 21, ОДТ.3 | `make reset` гарантированно возвращает к чистой БД |
| Защита от накопления артефактов между сессиями | Принцип минимизации данных, 152-ФЗ ст. 5 | `make reset` удаляет том; данные предыдущих сессий не остаются |
| Целостность образа | Приказ ФСТЭК № 239, ОЦЛ.1; OWASP ML05 | `make reset-hard` пересобирает образ с нуля; ONNX-модель верифицируется по SHA-256 |

### 14.5. Ограничения (честная оговорка)

| Механизм | Статус |
|---|---|
| VM-уровень изоляции (гипервизор) | Не реализован — только Docker |
| Автоматический сброс по расписанию | Не реализован (только ручной `make reset`) |
| Шифрование тома `tutor_data` | Не реализовано — до пилота требует оценки |
| Подпись Docker-образов (Docker Content Trust) | Не настроено — рекомендуется при переходе к пилоту |
