# Боевой хост: HTTPS через встроенный прокси

Стек публикуется за фронт-прокси Caddy, который терминирует TLS, сам выпускает
сертификат Let's Encrypt и продлевает его. Прокси описан в отдельном слое
`docker-compose.prod.yml` и в локальной разработке не участвует.

```
интернет ──443/80──▶ tutor-caddy ──внутренняя сеть──▶ tutor-frontend ──▶ tutor-backend
```

## Почему прокси, а не порт 80 у фронтенда

Nginx во фронтенд-контейнере отдаёт статику по HTTP и сертификатами не занимается.
Отдать ему порт 80 напрямую означало бы работу без HTTPS: браузеры показывают
предупреждение, а JWT и пароли идут по открытому каналу. Caddy закрывает это
одной строкой конфигурации и без ручного обновления сертификатов.

## Запуск

Домен передаётся переменной окружения — в репозитории он не зашит:

```bash
TUTOR_DOMAIN=tutor.example.ru \
  docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Ровно это делает `.github/workflows/deploy.yml` при пуше в `main`, беря домен из
переменной `TUTOR_DOMAIN` в настройках репозитория.

Отдельный `Caddyfile` не нужен: подкоманда `caddy reverse-proxy` включает
автоматический HTTPS для публичного домена сама.

## Что обязано быть выполнено до первой раскатки

1. **Домен резолвится на этот хост.** Проверить: `dig +short tutor.example.ru`.
2. **Порт 80 открыт наружу** — через него идёт ACME-проверка Let's Encrypt.
   Без него сертификат не выпустится, даже если нужен только 443.
3. **Порты 80 и 443 свободны.** Если их занимает посторонний веб-сервер,
   `docker compose up` честно упадёт с `port is already allocated`.

## Проверка

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://tutor.example.ru/
curl -sS https://tutor.example.ru/api/health
```

Ожидается `200` и `{"status":"ok"}`. Первый выпуск сертификата занимает несколько
секунд — шаг «Проверить HTTPS через домен» в workflow повторяет запрос десять раз.

WebSocket отдельной настройки не требует: `reverse_proxy` в Caddy v2 проксирует
upgrade-соединения прозрачно. Для тренажёра это критично — вся телеметрия идёт
через `/ws`.

## Почему сертификаты лежат в томе

`caddy_data` смонтирован как именованный том. Без него Caddy запрашивал бы
сертификат заново при каждой раскатке и за несколько деплоев подряд упёрся бы в
недельный лимит Let's Encrypt на выпуск для одного домена — после чего HTTPS
перестал бы подниматься до конца недели.

## Порты приложения наружу не смотрят

В `docker-compose.yml` публикации привязаны к loopback:

```yaml
- "127.0.0.1:8000:8000"   # API
- "127.0.0.1:8080:80"     # интерфейс
```

Снаружи доступен только Caddy. Прокси ходит к фронтенду по имени сервиса внутри
сети Docker, публикация ему не нужна. Локально `http://localhost:8080` работает
как прежде.
